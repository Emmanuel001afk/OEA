# OEA audit — 2026-10-31: confirmed findings and repair plan

Scope: the ten reported areas, mapped to the actual implementation in this
repository (branch `arena/9bde2e91-oea`, base `6ca0b74`). Every finding below
was confirmed by reading the code; nothing was assumed. Fixes are delivered
in batches, each with its own build and static-check run.

---

## 1. Control Center and Quick Settings

**Current implementation:** `power/OeaQuickControls.kt` (sheet built for
Home and the power overlay activity) + `notifications/OeaNotificationListener.kt`.

**Confirmed findings:**
- REAL and working: torch toggle (shared owner, true LED state), brightness
  slider (WRITE_SETTINGS flow with in-app fallback + permission deep link),
  three volume sliders (AudioManager), ringer mode segmented control (DND
  policy access), DND switch, notification list (from the listener, with
  open + "view all"), lock/power actions.
- **DECORATIVE (the reported problem):** Wi-Fi, Bluetooth, Auto-rotate,
  Location and Airplane mode rows only `startActivity()` the corresponding
  Settings screen. No state display, no toggle — exactly the "controls that
  merely appear functional" the task rejects.
- Dynamic Island positioning bug (below): see §1b.

**What Android actually allows an ordinary app (Android 13):**
- Bluetooth: **can be toggled** with the runtime permission
  `BLUETOOTH_CONNECT` (API 31+; legacy BLUETOOTH/BLUETOOTH_ADMIN ≤ 30) — a
  real toggle, real state.
- Auto-rotate: **can be toggled** via `Settings.System.ACCELEROMETER_ROTATION`
  with the already-used WRITE_SETTINGS flow — real toggle, real state.
- Wi-Fi: **cannot be toggled** by third-party apps since API 29
  (`WifiManager.setWifiEnabled` is system-only). Real state is readable; the
  compliant change surface is the in-place system panel
  (`Settings.Panel.ACTION_WIFI`).
- Airplane mode: cannot be toggled (system only); state readable via
  `Settings.Global.AIRPLANE_MODE_ON`; `Settings.Panel.ACTION_INTERNET_CONNECTIVITY`
  is the in-place surface.
- Location: cannot be toggled; mode readable; deep link only.
- Battery saver: cannot be toggled by apps (`DEVICE_POWER` is signature);
  state readable; deep link to Battery Saver.

**Repair (batch 1):** replace the five decorative rows with real-state rows:
Bluetooth real toggle (+ runtime permission flow, added to the manifest for
exactly this requirement), auto-rotate real toggle, Wi-Fi row showing real
state and opening the system Wi-Fi *panel* with an honest note about the
API-29 restriction, airplane/location/battery-saver real-state rows with
compliant actions. Every row keeps its honest explanation of what needs
system privilege.

### 1b. Dynamic Island below the camera

**Confirmed root cause (two layers):**
1. `OeaHomeTheme` does not set `android:windowLayoutInDisplayCutoutMode`,
   so the window uses the platform default, which does not render into the
   cutout area — a pill placed at the camera would be clipped.
2. `OeaDynamicIslandView.cameraPillTop()` anchors at
   `maxOf(statusBarHeight, cutout.bottom) + 3dp + userOffset` — i.e. always
   **below** the cutout, never centred on it. On a punch-hole phone the
   black pill hangs visibly under the camera dot instead of wrapping it.

**Repair (batch 1):** set `shortEdges` on the Home theme (guarantees the
window renders into the cutout region) and centre the pill vertically on
the cutout rect in portrait, keeping the stable landscape anchor, the user
fine-tune offsets and the reserved-height contract Home relies on. The
overlay-service island uses the same view, so the fix covers both.

## 2. Existing launcher applications (Camera, Image, VIP, Console, voice…)

**Confirmed findings:**
- Mini-app base (`miniapps/OeaMiniAppActivity.kt`) handles edge-to-edge
  insets and wraps sheets; `OeaPanelTheme` is opaque. No duplicate HOME
  path found; Phone and Call Blocker are separate modules (`phone/`,
  `callblocker/`) as required.
- The "settings screens fit / labels readable / nothing clipped / nothing
  of the underlying screen exposed" problems are per-sheet layout defects
  that need a systematic sweep of every `kit.sheet` builder (scrollability,
  text sizing, opaque backgrounds for translucent sheets). This is
  scheduled as its own batch with a checklist per mini-app, because doing
  it blind in the same pass as logic fixes would hide regressions.

**Repair (later batch):** sweep each mini-app's settings sheets: content in
a ScrollView, labels measured at the smallest supported width, controls not
clipped, translucent sheets given opaque scrims; verify on device.

## 3. Call Blocker reliability

**Current implementation:** `callblocker/OeaCallScreeningService.kt`
(CallScreeningService + `OeaCallBlockRules` in SharedPreferences) and
`callblocker/OeaCallBlockerActivity.kt` (UI, role handling).

**Confirmed findings (evidence, not assumptions):**
- Rules (exact/prefix/suffix, allow-list, contact exemptions) live in
  their own SharedPreferences keys and are **separate from history** —
  cleanup of history can already not touch rules by construction.
- History is **capped at 100 entries** and each blocked call does one
  read-modify-write of a StringSet — O(100) work. **History growth is NOT
  a plausible cause of blocking stopping.** The reported failure must come
  from elsewhere; the two candidates that survive the code read:
  1. **CALL_SCREENING role loss** — `onScreenCall` only fires while OEA
     holds the role; another screening app or a settings change silently
     revokes it, and nothing in OEA surfaces that.
  2. **OEM auto-launch/battery management** — XOS-class builds can refuse
     to start the app's manifest-declared service for a screening call;
     the call then rings through and OEA logs nothing.
- No retention configuration and no scheduled cleanup exist (only the hard
  100 cap). No screening decision log exists to distinguish "service never
  invoked" from "rules didn't match".

**Repair (batch 1):**
- Configurable history retention (Latest 100 entries / 7 days / 30 days /
  90 days / Keep until I clear).
- Automatic cleanup that runs (a) at every screening event, (b) when the
  blocker screen opens, and (c) once a day via AlarmManager — and only
  ever touches the history namespace.
- A screening decision log (last 50 decisions: number, verdict, reason,
  timestamp) displayed on the blocker screen with role status and
  last-screened-at, so the user can see on the phone whether the service
  is still being invoked — the evidence that distinguishes the two
  candidate causes above.
- Honest documentation of the XOS auto-launch requirement.

## 4. Console and Sound Amplifier

**Current implementation:** `miniapps/OeaConsoleApp.kt` (Sound Amplifier
sheet), `miniapps/OeaAmplifier.kt` (mic → earphone loopback with gain and
limiter), `miniapps/OeaVipAudioFx.kt` (VIP player session effects).

**Confirmed findings:**
- The amplifier is real (AudioRecord → AudioTrack with gain + limiter) but
  **mic-to-earphone only**, and stops when OEA leaves the foreground
  (documented honestly in the UI).
- The Console's "Equalizer & Bass" section is a NOTE + a settings link —
  there is no equalizer control in the Console at all. The only real EQ
  lives in the VIP player's audio sheet.
- No speaker/BT output path, no external-app audio amplification.

**What Android allows (to implement honestly):**
- The amplifier's OWN AudioTrack session can host real
  `Equalizer`/`BassBoost`/`Virtualizer` effects — a genuinely functional
  EQ for amplified audio.
- External-app media audio can only be captured with MediaProjection +
  `AudioPlaybackCaptureConfiguration` (API 29+, user consent per session,
  apps can opt out) — a real but consent-gated path to "amplify a movie".
- Speaker amplification of external audio has no ordinary-app path;
  BT/earbuds follow normal audio routing.

**Repair (later batch):** EQ on the amplifier session; playback-capture
amplifier mode with its consent flow; verified bass/volume controls;
documented limits. No claim of global amplification without a device test.

## 5. Device Information and Diagnostics

**Current implementation:** `miniapps/OeaConsoleApp.kt` `showDeviceInfo()` +
`deviceDetails()` — real data (Build, RAM, storage, screen, ABIs) but a
**flat list**, and diagnostics are scattered.

**Repair (later batch):** restructure into organised sections (Identity,
Processor, Memory, Storage, Battery incl. charging state + battery-health
where exposed, Display incl. refresh rate, Network/Connectivity, GPU where
queryable), each row still real-API-only and copyable; add the
device-diagnostics screen (performance, battery, memory, storage,
connectivity checks) distinct from the Stability Center (`fault/`), which
stays responsible for OEA launcher stability.

## 6. Icon and Appearance Manager

**Current implementation:** `icons/OeaIconController.kt` (icon packs via
appfilter.xml, themed icons API 33+, five shapes + system mask, disk cache,
fallback to the app's real icon when the pack has no mapping) and
`themes/`.

**Confirmed findings:**
- Pack support, fallbacks, shapes, monochrome/themed icons: present and
  real.
- **Missing:** per-app icon customisation (no way to pick an individual
  icon for one app), and no "dotted" shape.

**Repair (later batch):** per-component icon override store + "Change icon"
in the app long-press menu (choose from the installed pack's icons, the
system icon, or a gallery image), a dotted shape, and reset-to-default —
without changing launch identity (overrides stay cosmetic, keyed by
component).

## 7. Automatic App Recognition and Smart Folders

**Current implementation:** manual folders exist (`workspace/` +
`OeaWorkspaceStore.Folder`), a first-run "OEA" folder is seeded; **there is
no automatic family recognition at all** (nothing groups Google/Microsoft
apps).

**Repair (later batch):** a family catalogue keyed by package identifiers
(not display names), folder creation when ≥2 launchable family members
exist, updates on package add/remove, and user-override memory (apps the
user moves out are never re-added automatically; folders can be renamed/
dissolved). Ordinary unrelated apps stay as normal icons.

## 8. Offline Speech-to-Text

**Current implementation:** `voice/OeaSpeechEngine.kt` — Android's
`SpeechRecognizer` with `EXTRA_PREFER_OFFLINE`, command grammar, honest
limits ("no on-device model bundled").

**Confirmed finding:** there is no genuinely offline engine; recognition
still depends on the system/Google recognizer service.

**Repair (later batch):** a self-contained offline STT component
(reusable, no assistant logic) built on Vosk: runtime AAR via Maven
Central on the build runner, small (~40 MB) en-US model fetched by CI into
the APK (documented size cost) or on first use, model unzip + lifecycle +
RECORD_AUDIO handling, and a Voice-app toggle showing which engine is
active. Online recognition is never a mandatory dependency. This needs the
build workflow adjusted and must be verified on device before any
accuracy claims.

## 9. Home-Screen Data Accuracy

**Current implementation:** `workspace/OeaGlanceView.kt` (clock, chips:
battery, screen time) and `workspace/OeaDynamicIslandView.kt` (battery).

**Confirmed findings:**
- Battery data sources are correct (`ACTION_BATTERY_CHANGED`,
  `level*100/scale`, sticky read at registration) in both surfaces — but
  the glance battery chip is only **shown while charging or ≤20%**, so the
  "battery percentage on the home screen" is absent most of the time.
- **Screen-time bug (real):** `maybeQueryScreenTime()` sums
  `totalTimeInForeground` over all apps **excluding the launcher itself**,
  so the reported "Screen time" is systematically lower than the phone's
  actual screen-on time — the reported "incorrect figures" follow from
  this definition, not from a bad data source.
- Refresh cadence is fine (TIME_TICK + 60 s query guard + refresh on
  resume).

**Repair (batch 1):** include the launcher's own foreground time in the
screen-time total (System UI stays excluded, documented as "excludes lock
screen and shade"); show the battery chip always (still accurate, now
visible). No estimates substituted for measurements.
